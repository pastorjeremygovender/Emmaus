3. DAILY RHYTHM: DAILY OPEN STATE AND DAY ADVANCEMENT

The following behaviour is already correct and must remain:

- Daily Rhythm automatically opens on the user’s first app opening of each new local calendar day.
- It is not a lock on the rest of Emmaus.
- The user may navigate away without tapping Finished.
- The reminder system exists and otherwise works.

Current bug:

Because users can leave without tapping Finished, the previous day remains the active/open day forever. The next morning Emmaus reloads the same Daily Rhythm day, and the notification system suppresses the reminder because it thinks Daily Rhythm is already open.

Replace the old completion-dependent day advancement with date-based state.

Use separate concepts:

- assignedDay: the Daily Rhythm content day assigned to the user
- openedDate: the user’s local calendar date on which that assigned day was first opened
- completedAt: optional; only records that the user tapped Finished
- lastDailyRhythmActivityAt: optional activity timestamp

Required behaviour:

- The first time Daily Rhythm opens on a local calendar day, immediately and idempotently record that today’s assigned day was opened.
- Opening it counts as today’s Daily Rhythm having been acknowledged for progression purposes.
- Tapping Finished may record completion, but it must no longer be required for the next day to become available.
- When the next local calendar day begins, yesterday’s opened state must not suppress today’s reminder or today’s automatic opening.
- On the user’s first app launch on the new day, assign/open the next Daily Rhythm day exactly once.
- If the app is not opened before the configured reminder time, send the reminder for the new day.
- If today’s Daily Rhythm was already opened today, suppress duplicate reminders for today only.
- Reopening the app repeatedly on the same day must not advance multiple days.
- Refreshing, signing out/in, changing screens or using another device must not advance multiple days.
- Use the user’s saved timezone. If none exists, safely derive and save the device timezone. Do not calculate the daily boundary using UTC alone.
- Protect the advancement with a database transaction, unique constraint or atomic upsert so concurrent devices cannot create duplicate daily records.
- Do not mark the spiritual content “completed” merely because it opened. Keep “opened/acknowledged” and “Finished” distinct in reporting, while using opened/acknowledged for next-day progression.

Migration:

- Repair users stuck in a permanently open previous day.
- Do not skip several Daily Rhythm content days merely because several calendar days passed.
- Advance at most one content day when the user next returns.
- Preserve genuine completion history.

Test:
- First opening Monday opens Day 1 and records Monday.
- Leaving without Finished does not lock the app.
- A reminder can trigger Tuesday if the app has not been opened Tuesday.
- First Tuesday launch opens Day 2.
- Multiple Tuesday launches still show Day 2.
- Wednesday opens Day 3.
- Finishing remains recorded but is not required for progression.
- Test around midnight and across South African timezone boundaries.

Find and fix the actual first-save persistence failure.

- Await the database write before showing success or allowing navigation.
- Do not treat optimistic client state as proof of persistence.

INVESTIGATION REQUIREMENT FOR ISSUES 4 AND 5

Because both fail on first save but work on the second attempt, specifically inspect for:

- child content being saved before the new parent ID exists
- a temporary/client-generated ID used on first save
- missing await on mutations
- transaction ordering problems
- stale query cache
- create-versus-update branching errors
- race conditions caused by navigation
- database constraints or row-level security rejecting the first insert
- generation succeeding while persistence silently fails

Do not solve this with delayed timers, forced page refreshes or automatically running generation twice.
