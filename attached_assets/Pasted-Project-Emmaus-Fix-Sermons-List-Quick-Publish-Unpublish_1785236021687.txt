Project Emmaus — Fix Sermons List Quick Publish/Unpublish

Current status:

- Publish and Unpublish work correctly inside the Sermon editor.
- The Sermons list now shows explicit Publish/Unpublish actions.
- Clicking Publish or Unpublish on the Sermons list gives visual feedback as though the action ran.
- However, the sermon status does not actually change.
- The status badge remains unchanged.

Fix only the Sermons list quick publish/unpublish workflow.

Do not redesign the Sermons list.
Do not change the working editor publish/unpublish flow.
Do not alter Sermon Companion generation.
Do not change member-facing content architecture.

====================================================
EXPECTED BEHAVIOUR
====================================================

For a Draft sermon:

Click Publish
→ call the real sermon publish endpoint
→ persist Published status in the database
→ update the row badge to Published
→ replace Publish with Unpublish
→ update Overview counts
→ show “Published successfully.”

For a Published sermon:

Click Unpublish
→ show the existing confirmation if required
→ call the real sermon unpublish endpoint
→ persist Draft or Unpublished status according to the existing schema
→ update the row badge
→ replace Unpublish with Publish
→ update Overview counts
→ show “Unpublished successfully.”

The list action must use the same canonical server logic as the working editor action.

====================================================
TASK 1 — COMPARE LIST AND EDITOR HANDLERS
====================================================

Inspect the working Sermon editor Publish/Unpublish implementation.

Identify:

- endpoint;
- HTTP method;
- request body;
- status values;
- authentication requirements;
- API helper;
- cache invalidation;
- response shape;
- local state updates.

Then inspect the Sermons list quick-action handler.

Find the exact difference.

Likely failure points include:

- list button only changing temporary UI state;
- wrong sermon ID;
- using slug instead of database ID;
- incorrect endpoint;
- wrong HTTP method;
- missing credentials;
- request not awaited;
- response ignored;
- errors swallowed;
- wrong status value such as “published” versus “PUBLISHED”;
- mutating a stale object;
- list query not refreshed;
- optimistic update rolling back silently;
- event propagation opening another action;
- companion ID being passed instead of sermon ID.

Do not create a second publish implementation.

====================================================
TASK 2 — USE ONE SHARED PUBLISH SERVICE
====================================================

Extract or reuse one canonical sermon status service for both:

- Sermon editor;
- Sermons list.

unpublishSermon(sermonId)

or:

  sermonId,
  status
})

Both interfaces must call exactly the same API/service.

Do not duplicate fetch code with different request shapes.
