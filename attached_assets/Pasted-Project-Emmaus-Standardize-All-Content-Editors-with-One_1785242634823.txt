Project Emmaus — Standardize All Content Editors with One Shared Emmaus Content Editor

The Content Studio navigation has already been simplified and is now correct.

Do not redesign or revisit the top-level navigation.

Current Content Studio structure remains:

- Daily Rhythm
- Daily Devotionals
- Journeys
  - Collections
  - Standalone
- Sermon Companions
- Media Studio

The next task is to standardize the design and workflow inside the content editors.

At present, Daily Rhythm, Daily Devotionals, Journeys and Sermon Companions still use slightly different editor layouts, field arrangements, toolbar behaviour and preview patterns.

Create one shared Emmaus content editor experience across all four content types.

Do not change content architecture.
Do not merge content types.
Do not merge progress systems.
Do not redesign the member experience.
Do not remove working features.

====================================================
PRIMARY GOAL
====================================================

A pastor who learns to edit one type of Emmaus content should immediately know how to edit every other type.

Standardize:

- page header;
- breadcrumb;
- back navigation;
- toolbar;
- field layout;
- day navigation;
- live preview;
- save behaviour;
- publish behaviour;
- delete behaviour;
- loading states;
- success messages;
- spacing;
- typography;
- responsive layout.

The editor should feel like one application, not four separate tools.

====================================================
SHARED EDITOR COMPONENT
====================================================

Create or consolidate into one reusable component such as:

EmmausContentEditor

Use existing project naming conventions if an appropriate shared editor already exists.

The shared editor must support:

- Daily Rhythm Day
- Daily Devotional Entry
- Journey Day
- Sermon Companion Day

Do not create one giant component filled with content-type-specific conditional rendering.

Use a clear configuration or adapter pattern.

Suggested structure:

EmmausContentEditor
- EditorHeader
- ContentStudioToolbar
- DayNavigator
- FieldRenderer
- LiveMemberPreview
- Completion/Status feedback

Each content type should provide:

- editor title;
- parent title;
- breadcrumb items;
- content fields;
- renderer type;
- save callback;
- publish callback;
- unpublish callback;
- delete callback;
- back route;
- day-navigation data;
- content-type-specific labels.

====================================================
STANDARD DESKTOP LAYOUT
====================================================

Use the existing Daily Devotional editor as the visual source of truth.

Desktop layout:

LEFT PANEL

Editable fields

RIGHT PANEL

Live Member Preview

Recommended proportions:

- editor panel: approximately 42–48%
- preview panel: remaining width

Use the existing responsive widths if already working well.

Both panels may scroll independently where appropriate.

Keep the toolbar fixed or consistently visible according to the existing editor pattern.

Do not use a separate Preview page.

Do not use a Preview button.

====================================================
STANDARD MOBILE LAYOUT
====================================================

On smaller screens:

- show the editor first;
- provide a clear Editor / Preview segmented control or tabs;
- preserve all fields;
- preserve the exact member renderer;
- avoid horizontal scrolling;
- keep actions reachable;
- do not squeeze the side-by-side desktop layout into an unusable width.

Use the same data and renderer on mobile and desktop.

Do not create a simplified preview that differs from the member experience.

====================================================
SHARED TOOLBAR
====================================================

Reuse the approved shared Content Studio toolbar.

Exact action order:

Back

Save Draft / Save Changes

Publish / Unpublish

Delete

Rules:

- Back may be a left-side control while the other actions remain on the right, but the order and placement must remain consistent.
- New unsaved records do not show Delete.
- Draft records show Publish.
- Published records show Unpublish.
- Status badges remain informational only.
- Buttons disable while their own operation is running.
- Prevent duplicate requests.
- Use the shared delete confirmation workflow.
- Preserve existing Permanent Delete safeguards.

Do not create separate toolbar logic for each editor.

====================================================
STANDARD SAVE BEHAVIOUR
====================================================

Save Draft or Save Changes must:

- save the current fields;
- remain on the same screen;
- update the live preview state if needed;
- show a brief success message;
- never publish;
- never navigate away.

Standard success copy:

Draft saved successfully.

For already published content:

Changes saved successfully.

Use the same wording everywhere.

====================================================
STANDARD PUBLISH BEHAVIOUR
====================================================

Publish must:

- validate required fields;
- save pending changes;
- persist Published status;
- update the editor status badge;
- change Publish to Unpublish;
- refresh the parent list;
- refresh relevant member-facing discovery queries;
- show:

Published successfully.

Do not automatically publish parent or child records unless that behaviour is already explicitly established for that content type.

Preserve each content type’s publication rules.

====================================================
STANDARD UNPUBLISH BEHAVIOUR
====================================================

Use the shared confirmation dialog.

Heading:

Unpublish this content?

Body:

Members will no longer be able to access it.

Buttons:

Cancel

Unpublish

After success:

- status updates;
- button becomes Publish;
- parent list updates;
- member-facing caches refresh;
- show:

Unpublished successfully.

====================================================
STANDARD DELETE BEHAVIOUR
====================================================

Use the existing shared delete component and established cascade rules.

Do not invent new deletion behaviour.

Preserve:

- Daily Rhythm safeguards;
- Daily Devotional series/entry rules;
- Journey day and Journey rules;
- Sermon Companion cascade rules;
- existing Permanent Delete behaviour.

Only show Delete when valid for the current record.

====================================================
STANDARD DAY NAVIGATION
====================================================

Every multi-day content editor should use the same day-navigation pattern.

Supported examples:

- a compact horizontal Day 1 / Day 2 / Day 3 selector;
- a left-side day list;
- a dropdown on smaller screens.

Choose one pattern and reuse it consistently.

The day navigator should show:

- day number;
- title where space allows;
- Draft/Published state;
- current selection;
- Add Day action where valid.

Do not make Daily Rhythm, Daily Devotionals, Journeys and Sermon Companions use unrelated navigation designs.

====================================================
LIVE MEMBER PREVIEW
====================================================

The right panel must use the actual shared member renderer for the selected content type.

The preview must include where relevant:

- parent/series title;
- day number;
- title;
- runtime greeting personalisation;
- Scripture reference;
- embedded Scripture;
- reflection content;
- prayer;
- next step;
- closing;
- completion footer;
- Ask Emmaus;
- standard bottom navigation.

Do not build a separate visual approximation.

The editor preview and live member screen must share the same renderer.

====================================================
LIVE UPDATE BEHAVIOUR
====================================================

Editing a field should update the preview immediately.

Use debounced local state where needed.

Do not require:

- saving;
- page refresh;
- opening a preview route;
- clicking a preview button.

The preview may display unsaved local edits while the database remains unchanged until Save or Publish.

Clearly distinguish preview state from persisted state internally.

====================================================
SCRIPTURE PREVIEW
====================================================

All four content types must use the same shared Bible passage renderer.

Do not duplicate Scripture fetching.

The preview should:

- parse the current reference;
- use the selected preview/member translation;
- render the passage;
- show a clean loading state;
- show the established clean fallback;
- support Try Again and Open in My Bible where appropriate.

Do not hard-code Scripture text into records.

====================================================
GREETING PREVIEW
====================================================

All four content types must use the same shared greeting-personalisation utility.

Preserve the full authored greeting.

Personalise only the salutation or supported [name] token.

Never display:

- Super Admin;
- Member;
- undefined;
- null;
- an email address.

Preview and member experience must match.

====================================================
STANDARD LIST SCREENS
====================================================

Standardize the visual pattern of the parent list screens without forcing inappropriate data into one template.

Each top-level content list should use:

- page title;
- short description;
- primary New action;
- optional All / Draft / Published / Archived filters;
- consistent cards or rows;
- status badge;
- Edit;
- Publish/Unpublish where available;
- Delete.

Use the same:

- spacing;
- typography;
- status styles;
- button styles;
- empty states;
- loading skeletons;
- error states.

Do not turn all lists into wide desktop tables.

Prefer mobile-friendly cards or responsive rows.
