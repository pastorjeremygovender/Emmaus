Build Sprint 2 of the existing Project Emmaus application: the Minimum Viable Admin Portal.

This is an extension of the current working app.

Do not rebuild the user-facing app.
Do not replace the existing architecture.
Do not change the technology stack.
Do not remove or redesign the existing Walk, Bible, Journeys, Personal, authentication, demo mode, progress, reflection, prayer request, core journey, or sermon companion functionality.

Create a checkpoint before making changes.

## Sprint goal

Create a secure, simple administration area where an authorised pastor can manage Emmaus content without editing code.

The first version must allow an administrator to:

1. View the admin dashboard
2. View existing journeys
3. Create and edit journeys
4. Create and edit journey days
5. View and edit sermons
6. Review and publish Sermon Companion Journeys
7. View prayer requests
8. View basic user progress
9. Preview published content exactly as users will see it

This is a Minimum Viable Admin Portal.

Do not build the complete future church management platform yet.

## Preserve existing application

Do not change:

- existing public routes
- Firebase environment-variable names
- Firestore collection names already in use
- Firestore document IDs
- authentication logic
- demo mode
- user journey progress logic
- reflection saving
- prayer request saving
- sermon timestamp behaviour
- existing journey content
- existing bottom navigation
- existing user-facing visual design

The current application must continue working after this sprint.

## Admin route

Use the existing protected route:

/admin

If the route already exists, improve it rather than creating a duplicate.

Only authenticated users with an admin role may access it.

For demo mode, preserve the existing demo administrator access so the portal can be tested before Firebase roles are configured.

Unauthorised users should be redirected safely to the normal app.

Do not rely only on hidden navigation links for security.

## Admin design direction

The admin portal may use a desktop-oriented layout, but it must still work on tablets.

Use:

- clean white or warm-neutral background
- restrained Emmaus blue/teal accent
- clear left sidebar
- readable tables
- simple forms
- clear status labels
- generous spacing
- accessible controls

The admin portal should feel calm and professional.

Avoid:

- cluttered analytics dashboards
- excessive charts
- gradients
- animations
- competitive gamification
- unnecessary decorative elements

# 1. Dashboard

- Total users
- Active users in the last 7 days
- Journey completions in the last 7 days
- Open prayer requests
- Draft Companion Journeys awaiting review
- Published journeys

Use real Firestore data when Firebase is configured.

Recent activity

- Companion Journey approved

## Journey editor

Create a journey editor with fields:

- Title
- Description
- Journey type
- Duration in days
- Status
- Cover image URL or placeholder
- Optional church-wide flag
- Optional start date
- Optional end date

The sermon Companion Journey exemption must remain enabled by default.

## Journey days editor

Within the journey editor, display all days in order.

Each day should show:

- Day number
- Title
- Scripture reference
- Status
- Edit action

Provide:

+ Add Day

Allow administrators to:

- add a day
- edit a day
- delete a draft day
- reorder days
- duplicate a day

Do not allow silent deletion of a published day.

Require confirmation before deleting content.

- If no Companion Journey exists, create a five-day draft using clearly marked placeholder or existing demo content.
- Set its status to draft.
- Never publish it automatically.
- Link it to the sermon.

## Sermon Companion workflow

Use this exact workflow:

Draft
→ Pastoral Review
→ Approved
→ Published

Do not allow Draft to jump directly to Published without an explicit approval action.

Pastor edits must remain canonical and must not be overwritten by future regeneration.

Add a boolean or equivalent field indicating that content has pastor-approved edits.

## Form behaviour

All forms must have:

- required-field validation
- unsaved-changes warning
- saving state
- success message
- error message
- cancel action
- confirmation before destructive actions

Buttons must not appear to save when no save occurred.

## Publishing rules

Only approved content can be published.

A published journey must have:

- title
- description
- at least one day
- valid ordered day numbers
- Scripture reference for each day
- devotional reflection for each day
- prayer prompt for each day
- action step for each day

A Companion Journey must also have:

- linked sermon
- valid YouTube URL or a clearly marked placeholder in demo mode
- timestamp seconds where a sermon moment is used

Show validation errors clearly.

## Functional safety

Do not:

- open Firestore security rules
- weaken authentication
- make every user an administrator
- expose admin pages through ordinary bottom navigation
- publish generated content automatically
- overwrite pastor edits
- delete working user data
- replace the existing seed structures
- add unrequested features
