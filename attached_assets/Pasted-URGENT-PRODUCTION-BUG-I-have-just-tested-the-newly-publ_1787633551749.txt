The good news:

The bad news is CRITICAL:

Every navigation attempt reloads/reopens Daily Rhythm Day 1.

Examples I have personally reproduced in production:

- Tap Today's Steps in the bottom navigation → Daily Rhythm Day 1 opens again.
- Tap Today's Steps from the Previous Days screen → Daily Rhythm Day 1 opens again.
- Navigate away from Daily Rhythm → Day 1 is forced open again.
- The user cannot return normally to the rest of Emmaus.

This began after the per-launch startup-session fix.

DO NOT touch the Daily Rhythm progression rules.

The progression rules appear to be separate from this issue.

This is now specifically a STARTUP ROUTING / NAVIGATION GUARD bug.

MOST LIKELY CAUSE

The new "first opening / startup destination" logic appears to remain active after initial startup.

A per-launch Daily Rhythm destination may now be getting reapplied on ordinary in-app navigation.

Conceptually the current behaviour appears to be:

App launch
→ startup destination = DAILY_RHYTHM
→ open Day 1

THEN:

user taps Today's Steps
→ startup logic runs again
→ sees same launch session destination = DAILY_RHYTHM
→ forces Day 1 again

That is WRONG.

The persisted launch-session claim was created to ensure duplicate STARTUP requests from the same app launch return the same destination.

It must NOT mean:

"Every route request during this entire app session must return Daily Rhythm."

REQUIRED BEHAVIOUR

The startup redirect applies ONCE ONLY during app bootstrap.

→ startup decision
→ DAILY_RHYTHM
→ Daily Rhythm Day 1 renders successfully

AT THAT POINT THE STARTUP ROUTING PHASE IS FINISHED.

From then onward, normal Emmaus navigation must work.

→ Today's Steps

User taps My Bible
→ My Bible

→ Discover

User taps My Journey
→ My Journey

→ Previous Days

NONE of those actions may invoke or reapply the first-opening redirect.

IMPORTANT DISTINCTION

There are THREE separate concepts:

1. DAILY PROGRESSION STATE

Which 10 Minutes with Jesus Step is currently unlocked.

2. DAILY FIRST-OPEN STATE

Whether this user's first real Emmaus launch today should initially land in Daily Rhythm.

3. CURRENT IN-APP NAVIGATION

Where the user chooses to go AFTER Emmaus has launched.

These MUST remain independent.

The first-open state must NEVER override deliberate navigation after initial startup has completed.

REQUIRED STARTUP LIFECYCLE

Implement an explicit startup lifecycle.

Conceptually:

APP_BOOTSTRAPPING
→ resolve startup destination

If Daily Rhythm:
→ navigate to Daily Rhythm

Once Daily Rhythm route has successfully rendered:
→ mark this CLIENT LAUNCH as STARTUP_ROUTING_COMPLETE

After "STARTUP_ROUTING_COMPLETE":

DO NOT call the startup redirect logic during ordinary route changes.

DO NOT redirect the user back to Daily Rhythm.

DO NOT consult the startup destination to override navigation.

The persisted launch-session claim may remain server-side for duplicate startup-request consistency, but the client must stop treating it as an active redirect after initial startup resolution.

CRITICAL

Do not solve this by changing the server to say Today's Steps immediately after the first request.

That would recreate yesterday's original race condition:

Request 1 → Daily Rhythm
Request 2 → Today's Steps

The correct solution is:

Duplicate requests DURING BOOTSTRAP
→ all consistently return Daily Rhythm.

But once bootstrap has successfully completed
→ startup routing ends.

Ordinary application navigation is then completely independent.
