EMMAUS VOICE — PHASE 1: REPLACE THE CURRENT VOICE PROTOTYPE

IMPORTANT: READ THIS ENTIRE PROMPT BEFORE CHANGING CODE.

The current “Hear Emmaus” button and browser/system text-to-speech implementation are now obsolete.

They may be removed completely.

Do not patch, restyle or extend the current button.

Build a new unified Emmaus Voice architecture inside the EXISTING Emmaus application.

This is a major user mode, not a page-specific playback button.

The long-term purpose is to let people use Emmaus naturally:

- while driving;
- while exercising;
- while working;
- while cooking;
- when they cannot comfortably read a screen;
- when they prefer listening and speaking.

The final architecture must support:

1. Natural spoken Bible reading.
2. Natural spoken devotionals and Walk Steps.
3. Spoken Ask Emmaus answers.
4. Future realtime voice conversations.
5. Future hands-free navigation and playback control.
6. Background-friendly audio playback.
7. One consistent Emmaus voice identity.

Starting generated narration must pause sermon audio.

==================================================

Do not use browser SpeechSynthesis for primary Emmaus narration.

Select one temporary natural Emmaus voice for Phase 1.

The voice should feel:

- warm;

- natural;

NARRATION MODE
For:

Characteristics:
- slightly slower;

CONVERSATION MODE
For:
- Ask Emmaus answers;
- prompts;

- future voice conversation.

Characteristics:
- natural;
- responsive;
- shorter pauses;
- conversational pacing.

Do not create completely unrelated voice identities.

==================================================
SERVER-SIDE API
==================================================

Create authenticated server endpoints for speech generation.

Example concepts:

POST /api/voice/speech
POST /api/voice/prepare-content
GET /api/voice/audio/:id
GET /api/voice/resume
PUT /api/voice/resume
DELETE /api/voice/cache/:id where authorised

Never expose provider API keys to the browser.

Validate:

- authentication;
- church/tenant;
- source content access;
- input length;
- supported content type;
- requested voice;
- requested speaking style.

Do not allow the client to submit arbitrary unlimited text for unrestricted speech generation.

Prefer source IDs:

- bible book/chapter;
- devotional ID;
- Walk Step ID;
- sermon ID/section ID;
- Ask Emmaus message ID.

The server should retrieve and verify canonical text itself.

==================================================
AUDIO CHUNKING
==================================================

Long content must be divided into natural sections.

Do not send an entire Bible book or long transcript as one request.

Chunk at:

- headings;
- paragraphs;
- Scripture sections;
- devotional sections;
- sermon sections.

Each chunk must store:

- source type;
- source ID;
- sequence;
- text hash;
- voice;
- style;
- audio object path;
- duration;
- created at.

Playback must sound continuous.

Preload the next chunk before the current chunk ends.

Avoid audible gaps where possible.

==================================================
AUDIO CACHE
==================================================

Do not regenerate identical content every time.

Cache generated audio using a deterministic key based on:

- canonical content ID;
- content version;
- prepared-text hash;
- selected voice;
- narration style;
- speaking speed.

Store generated audio in persistent object storage.

When content changes:
- invalidate only affected audio;
- do not invalidate unrelated chapters or devotionals.

Allow streaming before the full item has finished generating where technically practical.

Do not make first playback wait for an entire long chapter if the first section is ready.

==================================================
PLAYBACK PROGRESS
==================================================

Persist user progress for:

- source type;
- source ID;
- chunk;
- playback seconds;
- completed status;
- last played at.

Resume accurately across:

- browser refresh;

- leaving and returning;
- temporary network interruption.

Do not change discipleship completion merely because audio played.

Existing completion rules remain authoritative.

When the user reaches the correct completion point, use the existing completion action rather than inventing a separate voice-progress system.

==================================================
ERROR HANDLING
==================================================

Never show a blank or frozen voice screen.

Handle:

- microphone permission not relevant in Phase 1;
- speech generation failure;
- missing content;
- invalid source ID;
- expired audio cache;
- network loss;
- object-storage failure;
- unsupported browser media controls;
- interrupted playback.

Show:

“We couldn’t prepare this audio.”

Actions:
- Try Again
- Read Instead
- Back

If a later chunk fails:
- preserve current position;
- retry that chunk;
- do not restart the whole item.
