The Supabase Auth migration is functioning and confirmation emails are being delivered successfully through Resend.

However, real-device/account testing has exposed two issues that MUST be fixed before publishing.

DO NOT PUBLISH.

ISSUE 1 — NEW USER IS INHERITING EXISTING USER DATA

I created a completely new Supabase Auth account using a new email address.

After confirming the email and entering Emmaus, the new user received existing Today's Steps/progress/content state that had already been used during testing.

This is incorrect and is a serious user-data isolation issue.

A brand-new verified Supabase account must NEVER inherit:

* another user's Today’s Steps state
* Walk/Journey progress
* active Walks/Journeys
* Daily Rhythm completion history
* devotional progress
* sermon progress
* Bible notes/progress
* Groups state
* pastoral/member data
* preferences
* saved content
* testing/demo data
* any other user-scoped information

INVESTIGATE FIRST

Trace exactly how a newly authenticated Supabase auth_user_id is mapped to user_profiles and all user-scoped application data.

Specifically investigate whether:

* new Supabase users are being attached to one of the two legacy user_profiles rows
* a demo/default user ID is still being used anywhere
* progress queries still fall back to demo-user-1 or another shared identity
* new profile creation clones/defaults from an existing profile
* email is being used incorrectly to select an existing profile
* missing profile IDs cause queries to return global/shared test data

Do not fix this by clearing the existing production/testing data.

Fix the identity boundary.

REQUIRED NEW-USER BEHAVIOUR

For every genuinely new verified Supabase account:

1. Create a new unique Emmaus user_profile associated with that exact verified Supabase auth_user_id.
2. Default app_role to `user`.
3. Do not associate the account with either legacy profile automatically.
4. Do not copy progress/state from another user.
5. All user-scoped queries and writes must use the verified authenticated user's mapped profile/person identity.
6. No fallback to a shared/demo identity may occur in production.

A new user should begin Emmaus in the intended clean starting state.

For Today's Steps specifically, a new user should initially receive only the standard default starting experience:

* Daily Rhythm available
* other standard default cards displayed in their fresh/unstarted state where applicable
* no previously completed days
* no previously started Walks or Journeys
* no inherited progress or activity

Do not remove the legitimate default-content rules. The problem is inherited user state, not the existence of default content.

USER ISOLATION TEST

Verify:

* activity performed by B does not appear for A

* Today’s Steps

* sermons
* Bible/user notes
* favorites
* Groups

* pastoral/member state

Confirm that every user-specific query is scoped to the authenticated verified identity/profile.
