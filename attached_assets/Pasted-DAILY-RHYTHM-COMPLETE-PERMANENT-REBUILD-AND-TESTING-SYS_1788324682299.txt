DAILY RHYTHM — COMPLETE PERMANENT REBUILD AND TESTING SYSTEM

Daily Rhythm, particularly 10 Minutes with Jesus, is the heart and foundational feature of Emmaus. It has repeatedly worked briefly and then broken again after other adjustments.

Do not apply another narrow patch to the current symptom.

Trace and correct the entire Daily Rhythm system across the database, server, client, app launch, navigation, notifications, caching, PWA resume behaviour, completion actions and progress history. There must be one authoritative system used by every Daily Rhythm entry point.

CURRENT FAILURE

This morning:

- The Daily Rhythm notification was received.
- Emmaus did not automatically open onto Daily Rhythm.
- The user was not trapped inside 10 Minutes with Jesus.
- Daily Rhythm had not advanced to a new day.
- It was still displaying yesterday’s content.
- Yesterday was itself still displaying the previous day because Continue had not been pressed.
- Therefore the Daily Rhythm was effectively stuck on an older day.

Today’s automatic opening cannot currently be verified. Because the correct new day was never resolved, we cannot determine whether:

- the automatic-opening rule failed;
- the system incorrectly believed today’s Daily Rhythm had already been opened;
- yesterday’s opened state was reused for today;
- a cached route or last-viewed page was restored;
- or the old Daily Rhythm day prevented today’s automatic opening.

Do not assume that automatic opening works because a notification was received or because the user was not trapped in Daily Rhythm. Correct-day progression and automatic opening must both be tested independently and together.

NON-NEGOTIABLE PRODUCT BEHAVIOUR

Daily Rhythm must:

1. Advance automatically according to the user’s local calendar date.
2. Open automatically once on the user’s first app opening each new local day.
3. Allow the user to navigate away immediately without pressing Continue, Finished or Complete.
4. Never repeatedly force the user back into Daily Rhythm during the same day.
5. Allow every previously available day to be reviewed.
6. Never make a missed or unfinished day block today’s day.
7. Never make a navigation or completion button control calendar progression.
8. Keep My Bible available at all times, regardless of Daily Rhythm state.
9. Work consistently across refreshes, app restarts, devices, notification links and PWA resume.
10. Be fully testable without waiting for real calendar days to pass.

CORE PROGRESSION RULE

The Daily Rhythm day available today must be determined only by:

1. The user’s Daily Rhythm start/enrolment date.
2. The current calendar date in the user’s local timezone.
3. The sequence and publication status of Daily Rhythm content.

It must never be determined by whether the user previously pressed:

- Continue;
- Finished;
- Complete;
- Back to Today’s Steps;
- or any other navigation button.

Example:

- User begins Daily Rhythm on 1 September.
- 1 September = Day 1.
- 2 September = Day 2.
- 3 September = Day 3.

On the first opening of Emmaus on 3 September, Day 3 must be shown even if the user:

- did not press Continue on Day 1;
- did not press Finished on Day 2;
- completely missed Day 2;
- navigated away while reading;
- closed the app while reading;
- refreshed the PWA;
- left the app open overnight;
- opened from a notification;
- cleared a temporary client cache;
- or signed in on another device.

Buttons must not control progression.

ONE AUTHORITATIVE DAILY RHYTHM RESOLVER

Create one authoritative Daily Rhythm resolver and require every part of Emmaus to use it.

It must resolve:

- the user’s local calendar date;
- the user’s timezone;
- the user’s Daily Rhythm start date;
- the correct day number available today;
- the corresponding published content ID;
- whether today’s exact content has been opened today;
- whether the user is intentionally reviewing a past day;
- and whether the app should automatically open today’s content.

Search the entire codebase for all competing logic that calculates, increments, stores, restores, redirects or assumes the current Daily Rhythm day.

This includes:

- initial app startup;
- authentication and post-login routing;
- Today’s Steps;
- the Daily Rhythm reader;
- notification creation;
- notification deep links;
- completion screens;
- Continue, Finished and Complete actions;
- Back to Today’s Steps;
- local storage;
- session storage;
- cached database queries;
- service-worker caches;
- PWA install and resume logic;
- page visibility and foreground events;
- route guards;
- progress hooks;
- server APIs;
- database functions and triggers;
- user progress records;
- content publication logic;
- admin previews;
- and cross-device synchronisation.

Remove or replace any competing day calculation. Do not leave multiple systems capable of choosing the current Daily Rhythm day.

SEPARATE THE STATES

Do not use one progress value or boolean to represent several different things.

Maintain separate states for:

1. todayAvailableDay
   The day calculated from the user’s start date and current local calendar date.

2. todayContentId
   The published Daily Rhythm content resolved for todayAvailableDay.

3. lastOpenedDay
   The most recent Daily Rhythm day opened by the user.

4. lastOpenedContentId
   The exact content item most recently opened.

5. openedAt
   When a Daily Rhythm day was first opened.

6. openedLocalDate
   The user’s local calendar date on which it was opened.

7. completedDay
   Whether the user explicitly pressed Finished or Complete.

8. completedAt
   When explicit completion occurred.

9. reviewDay
   A past day deliberately selected by the user.

10. notificationState
    Whether today’s exact Daily Rhythm content has been opened on today’s exact local date.

These values must not overwrite or incorrectly control one another.

The state used to prevent repeat automatic opening must be keyed by both:

- the resolved Daily Rhythm content/day;
- and the user’s local calendar date.

Do not use an undated permanent boolean such as:

dailyRhythmOpened = true

That kind of value will incorrectly suppress future days.

CORRECT-DAY OPENING BEHAVIOUR

Whenever Daily Rhythm is opened normally:

1. Calculate todayAvailableDay fresh using the authoritative resolver.
2. Resolve the corresponding published content.
3. Open today’s content by default.
4. Do not restore yesterday’s content merely because it was the last viewed item.
5. Do not allow stale local storage, a cached route, an old content ID or retained component state to override todayAvailableDay.
6. Only display an earlier day when the user deliberately selects it from the past-days list.
7. Leaving a past-day review and reopening Daily Rhythm normally must return to today’s day.
8. Refreshing while deliberately reviewing a past day may preserve the review within that review route, but must never change which day is considered today.
9. Today’s Steps must always display the correct current Daily Rhythm day and status.

AUTOMATIC OPENING ONCE PER DAY

On the user’s first normal app launch or first return to the foreground on each new local calendar day:

1. Recalculate todayAvailableDay.
2. Resolve todayContentId.
3. Check whether that exact content has been opened on that exact local date.
4. If it has not been opened today, automatically open today’s Daily Rhythm.
5. Once it opens, immediately record that today’s exact content was opened on today’s local date.
6. The user must then be free to navigate away without pressing Continue, Finished or Complete.
7. Do not automatically reopen it repeatedly during the same local day.
8. Reviewing a past day must not count as opening today’s day.
9. Yesterday’s opened or completed state must never suppress today’s automatic opening.
10. A stale route, cached page or last-viewed content ID must never override the new-day calculation.

If Emmaus remains open overnight, returning to the foreground after the local date changes must:

- invalidate the previous day’s resolved state;
- recalculate todayAvailableDay;
- and automatically open today’s Daily Rhythm once if it has not yet been opened.

BIBLE EXEMPTION

My Bible must always remain available.

Daily Rhythm automatic opening must not become a navigation lock.

If the user deliberately opens My Bible directly, including through a Bible link or deep link, permit access without forcing Daily Rhythm first.

Daily Rhythm may be the normal first screen of the new day, but users must be able to navigate away immediately and use the Bible or any other permitted area of Emmaus.

CONTINUE, FINISHED AND COMPLETE

These actions may:

- record explicit completion;
- display a completion screen;
- navigate within the current experience;
- provide access to the past-days list;
- return to Today’s Steps.

They must not:

- unlock tomorrow’s content;
- determine which day appears tomorrow;
- advance the user to tomorrow’s content early;
- prevent tomorrow’s content from appearing;
- modify the user’s start date;
- change todayAvailableDay;
- or control the next calendar day.

If the user never presses any of these buttons, tomorrow must still advance correctly.

COMPLETION SCREEN

When the user presses Finished or Complete:

- show the Daily Rhythm completion screen;
- keep it visible;
- do not automatically redirect before the user chooses an option;
- allow the user to choose Back to Today’s Steps or review past days;
- do not reload the same Daily Rhythm unexpectedly;
- do not trap the user in a redirect loop.

PAST DAYS AND HISTORY

The user must be able to review every Daily Rhythm day that became available from their start date through today.

This includes days they:

- completed;
- opened but did not complete;
- or did not open at all.

Future days must remain unavailable.

Show accurate statuses:

- Completed — the user explicitly pressed Finished or Complete.
- Opened — the user opened that day but did not explicitly complete it.
- Missed — the day became available but the user never opened it.

A missed, opened-but-incomplete or partially viewed day must never block today’s day.

Selecting a past day is review mode. It must not:

- change todayAvailableDay;
- overwrite todayContentId;
- suppress today’s notification;
- mark today as opened;
- alter the user’s start date;
- or become the default day on the following app launch.

NOTIFICATIONS

The daily notification must correspond to todayAvailableDay and todayContentId.

Notification suppression must be based only on whether today’s exact Daily Rhythm content has already been opened on today’s exact local date.

The following must not suppress today’s notification:

- opening yesterday’s content;
- reviewing a past day;
- an old lastOpenedDay value;
- a completion record from yesterday;
- a stale local-storage flag;
- or an app session that remained open overnight.

When the user taps the notification:

1. Open Emmaus.
2. Recalculate todayAvailableDay.
3. Resolve todayContentId.
4. Navigate directly to today’s Daily Rhythm.
5. Never reopen yesterday’s cached or last-viewed day.
6. Record today as opened only when today’s resolved content is actually opened.

Receiving the notification does not prove that automatic app-opening logic works. Test notifications and normal app launches separately.

TIMEZONE AND DATE HANDLING

Use the user’s local calendar date consistently across:

- client calculations;
- server calculations;
- database records;
- notification scheduling;
- automatic-opening checks;
- and reporting.

Do not calculate progression using elapsed 24-hour periods.

A calendar day changes at midnight in the user’s effective local timezone, even if fewer or more than 24 hours have elapsed because of timezone or daylight-saving changes.

Use a clear timezone priority:

1. The timezone stored in the user’s profile, if available and valid.
2. Otherwise the device/browser timezone.
3. Otherwise the configured church/default timezone.

Store timestamps in UTC, but calculate Daily Rhythm calendar dates in the effective user timezone.

Do not mix UTC calendar dates with local calendar dates.

PUBLISHED CONTENT SAFETY

Only published Daily Rhythm content may be delivered to normal users.

The resolver must use the authoritative sequence/order field, not an unreliable UI position or arbitrary database-return order.

If todayAvailableDay points beyond the published Daily Rhythm content:

- do not crash;
- do not show a draft;
- do not silently reset the user to Day 1;
- do not incorrectly reopen an old day as though it were today;
- show the latest valid published day with an appropriate “You’re up to date” state;
- and create a clear administrative warning that future Daily Rhythm content must be published.

Also verify that all 30 published Daily Rhythm days are correctly discoverable by the resolver. Do not assume only the first five items exist because an admin list is paginated or only five items are visible.

CACHE AND PWA SAFETY

Daily Rhythm data must not become stale across calendar days.

Review:

- service-worker cache strategy;
- cached API responses;
- React/query cache or equivalent;
- persisted client state;
- last-route restoration;
- browser back/forward restoration;
- PWA cold launch;
- PWA warm resume;
- visibility-change handling;
- online/offline transitions.

Static assets may be cached normally, but date-sensitive Daily Rhythm resolution must be revalidated when:

- the app launches;
- authentication completes;
- the app returns to the foreground;
- the local date changes;
- a notification is tapped;
- the Daily Rhythm route is opened;
- or the user changes device/timezone.

Do not briefly display an old Daily Rhythm day before replacing it with today’s day. Show a calm loading state while the authoritative resolver runs.

CROSS-DEVICE BEHAVIOUR

The server/database must remain the authoritative source for:

- the user’s start date;
- opened history;
- completion history;
- and the correct content sequence.

Local storage may improve performance but must not override authoritative server state.

When the user signs in on another device, the same correct day must be available and their legitimate history must remain intact.

MIGRATION OF EXISTING USERS

Existing users may have inconsistent progress caused by the previous logic.

Do not reset users to Day 1.

Do not erase legitimate history.

Do not change their genuine Daily Rhythm start date unless it is missing or provably invalid.

On first load after this rebuild:

1. Preserve the original start date.
2. Calculate which day should be available today.
3. Preserve explicit completion records where they exist.
4. Preserve valid opened records where they exist.
5. Make all earlier eligible days reviewable.
6. Ignore stale current-day, last-route and client-cache values that conflict with the authoritative calculation.
7. Do not allow a previously unfinished day to block today.

If legacy data is ambiguous, migrate conservatively and log what was repaired.
